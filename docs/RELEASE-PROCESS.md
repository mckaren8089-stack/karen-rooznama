# رویه انتشار و نسخه‌بندی روزنمای کارن

این سند فنی برای نگهداری نسخه‌های اپ و جلوگیری از انتشار ناقص است. README عمومی فقط معرفی کوتاه محصول و لینک اجرای مستقیم است.

## وضعیت مصوب
- محصول فعلی: وب‌اپ قابل نصب PWA با پشتیبانی آفلاین پس از بارگیری اولیه؛ تغییر به APK در آینده جداگانه بررسی می‌شود.
- **مرجع نسخه اجرایی:** مقدار `VERSION` در `sw.js`، در قالب `karen-rooznama-vX.Y.Z`. تغییر آن یعنی نسخه جدید کش و دریافت مجدد همه فایل‌های اصلی بدون پاک‌کردن یادداشت‌ها.
- `manifest.webmanifest` برای `id`، `scope` و `start_url` هویت پایدار نصب است؛ **این‌ها نسخه برنامه نیستند و نباید برای هر انتشار تغییر کنند.**
- آزمون‌های آفلاین مقدار نسخه را مستقیماً از `sw.js` می‌خوانند؛ شماره نسخه دیگری در آزمون نوشته نمی‌شود.
- `scripts/check-release.mjs` در CI و پیش از انتشار، هویت PWA، پوشش فایل‌های آفلاین، نسخه کش، آیکون‌ها پس از ساخت و نسخه Actionهای GitHub را بررسی می‌کند.

## مراحل انتشار
1. تغییرهای لازم فقط در کد و آزمون‌ها انجام شوند؛ داده خصوصی کاربران وارد مخزن، Issue یا لاگ عمومی نشود.
2. اگر فایل‌های خود PWA یا داده آفلاین تغییر کرده‌اند، `VERSION` در `sw.js` افزایش یابد.
3. GitHub Actions تست‌ها را در دو محیط **Ubuntu 24.04** و **Ubuntu 26.04** اجرا کند.
4. انتشار GitHub Pages فعلاً روی **Ubuntu 24.04** ثابت است تا جابه‌جایی `ubuntu-latest` غافلگیرکننده نباشد.
5. در Deploy، اسکریپت صحت نسخه و آیکون‌ها کنترل شود و سپس Pages منتشر شود.
6. موفق‌شدن CI و Deploy، نصب موفق در تمام گوشی‌ها را تضمین نمی‌کند؛ در تغییرهای مهم PWA، نمونه واقعی روی اندروید بررسی شود.
7. اگر فایل‌ها یا Service Worker تغییر کرده‌اند، بازشدن با اینترنت و سپس حالت آفلاین پس از فعال‌شدن نسخه جدید کنترل شود؛ **بدون پاک‌کردن Site Data یا یادداشت‌ها**.

## مرز نسخه‌بندی
- فایل README عمومی نیازی به نمایش دائمی شماره نسخه ندارد.
- تاریخ جلسه، ساعت شخصی و گزارش‌های عیب‌یابی در README ثبت نشوند.
- ثبت فنی، گزارش آزمون و برنامهٔ توسعه در `docs/` و مرکز مادر نگه داشته شوند.
- `LICENSE` فعلی اعلام «تمامی حقوق محفوظ» است؛ داده رسمی دانشگاه تهران و حقوق شخص ثالث مستقل‌اند.

## حفاظت شاخه اصلی — اقدام دستی باقی‌مانده
شاخه `main` فعلاً با رابط کاربری GitHub محافظت نشده است؛ اتصال فعلی قابلیت نوشتن Ruleset یا Branch Protection را ارائه نمی‌کند.

پیشنهاد کم‌خطر، در **Settings → Rules → Rulesets → New branch ruleset**:
- هدف: فقط **Default branch**، یعنی `main`.
- **Restrict deletions** را فعال کن.
- **Block force pushes** را فعال کن.
- در حال حاضر **Require a pull request before merging**، **Restrict updates** یا الزام بررسی امضای Commit را روشن نکن؛ این‌ها ممکن است ویرایش مستقیم از ChatGPT/گوشی را مختل کنند.
- پس از ذخیره، در صفحه شاخه `main` وضعیت حفاظت را بررسی کن.

این تنظیمات، امنیت کامل یا جایگزین بازبینی تغییرات نیستند؛ فقط از دو عمل پرخطر محافظت می‌کنند. در آینده پس از طراحی شاخه‌بندی و روند PR می‌توان الزام‌های بیشتر اضافه کرد.
